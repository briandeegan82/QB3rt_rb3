QB3rt Fleet — Network Architecture & Ansible

How the 14 RB3 Gen 2 units, the ROS 2/DDS layer, and the Ansible tooling in this repo fit together. Reflects the state of the repo as of the lab-and-demo-nodes branch.

1. Physical network layout

The fleet is split across two separate, non-bridged Wi-Fi networks to load-balance 14 devices across two APs:

NetworkSSIDSubnetMembers
ODDROS_NET_ODD192.168.1.0/24units 1, 3, 5, 9, 11, 13, 15
EVENROS_NET_EVEN192.168.2.0/24units 2, 6, 8, 10, 12, 14, 16

Each unit's static IP matches its id on its own subnet (192.168.<1|2>.<id>), with one legacy exception: unit 1 is 192.168.1.101 rather than .1 (pre-dates the current per-id convention). A hidden reserve SSID, UoGPSK, is configured fleet-wide as a fallback and never auto-connects.

The two networks are not bridged/routed. A laptop on one subnet cannot reach units on the other — there is no L3 path between them. To reach the other half you must physically switch your Wi-Fi association (see §5).

2. ROS 2 / DDS setup

Domain IDs

Every unit's ROS_DOMAIN_ID equals its unit id (e.g. qb3rt-6 → domain 6). On the robot this is written to /etc/qb3rt/domain_id by stamp/stamp_unit.sh and read at login by /etc/profile.d/qb3rt-ros-env.sh (system/qb3rt-ros-env.sh in the repo). Note that domain id and IP address are two independent numbers — don't assume they match (unit 1 is domain 1 but IP .101).

Middleware: CycloneDDS, unicast-only

The fleet standardises on CycloneDDS (RMW_IMPLEMENTATION=rmw_cyclonedds_cpp) rather than the default FastRTPS, because the lab APs have multicast disabled (ansible/roles/ros2_demo_nodes/defaults/main.yml). ROS 2's normal zero-config discovery relies on multicast SPDP announcements — with that off, every participant needs an explicit unicast peer list or it discovers nothing.

Each robot's CycloneDDS config (deployed from system/cyclonedds.xml to /etc/qb3rt/cyclonedds.xml) sets:

<Domain Id="any">         <!-- follows whatever ROS_DOMAIN_ID is exported -->
  <AllowMulticast>false</AllowMulticast>
  <NetworkInterface name="wlan0"/>
  <Peers>
    <Peer address="localhost"/>
    <Peer address="192.168.0.101"/>   <!-- stale: pre-dates the ODD/EVEN split -->
  </Peers>
</Domain>
Known gap: the robot-side peer list still only names 192.168.0.101, a single address from the old pre-split 192.168.0.0/24 network. In practice this doesn't block laptop-initiated discovery — once the laptop announces itself to a robot's real IP, RTPS discovery converges bidirectionally regardless of what the robot's own peer list says — but it means robot-to-robot discovery on the current subnets is effectively unconfigured. Worth cleaning up in system/cyclonedds.xml if multi-robot coordination is ever needed.

Large-message tuning (camera frames, costmaps) also lives here: SocketReceiveBufferSize/SocketSendBufferSize raised past the kernel's ~208 kB default, backed by net.core.rmem_max in /etc/sysctl.d/98-agv-dds.conf.

Laptop-side DDS config

The laptop needs its own CycloneDDS peer list, kept outside this repo at ~/cyclonedds.xml (referenced by laptop/qb3rt_env.sh via CYCLONEDDS_URI). For fleet-wide monitoring it should list every unit's static IP as an explicit unicast peer, e.g.:

<Domain Id="any">
  <NetworkInterface name="wlp4s0"/>     <!-- match your active fleet-net NIC -->
  <AllowMulticast>false</AllowMulticast>
  <Discovery>
    <MaxAutoParticipantIndex>16</MaxAutoParticipantIndex>
    <Peers>
      <Peer address="localhost"/>
      <Peer address="192.168.1.101"/> <!-- qb3rt-1  -->
      <Peer address="192.168.1.3"/>   <!-- qb3rt-3  -->
      <!-- ...one Peer per unit, both subnets; the unreachable
           half is simply ignored while on the other Wi-Fi -->
    </Peers>
  </Discovery>
</Domain>
Keep MaxAutoParticipantIndex modest (10–20) on a monitoring laptop. With multicast off, CycloneDDS probes participant indexes 0..MaxAutoParticipantIndex per peer — a 14-peer list × 120 (a value copied from a dense single-robot Nav2 config where many local participants were expected) multiplies into thousands of unicast probes and visibly delays discovery of whichever peer's turn comes late in the cycle. Each robot only ever runs a handful of nodes, so a small value is enough and discovery converges in a couple of seconds instead of 10–20+.
ros2's background CLI daemon caches its DDS config at daemon startup, per domain. If you edit cyclonedds.xml, run ros2 daemon stop (or pkill -f ros2-daemon) before retesting — otherwise you'll be silently talking to a daemon that's still running the old config, which looks identical to a network fault (ros2 topic list hangs or returns nothing).

The IMU driver specifically

The onboard ICM-42688 IMU is published by qrb_ros_imu. Two ways to bring it up:

  • ros2 run qrb_ros_imu imu_node — raw node, publishes bare /imu. Good for a quick connectivity smoke test.
  • ros2 launch QB3rt imu.launch.py (pulled in by odometry_bringup.launch.py/full_stack.launch.py) — the production path: loads it as a composable node and remaps to /imu/data, which is what config/ekf.yaml's EKF actually subscribes to.

Either way, the node talks to a lower-level sensor-service systemd unit (the Qualcomm sensor HAL, /usr/bin/sensor_service) over a local socket. If imu_node logs repeated SensorClient: please check if the sensor service ... is running and eventually exits after ~30 retries, the HAL daemon itself has gone idle/stuck — sudo systemctl restart sensor-service on the unit, then relaunch imu_node, resolves it (observed on 2 of 14 units during a 2026-09-20 fleet sweep).

3. Ansible for fleet management

Ansible content lives under ansible/ and is the newest tooling layer in the repo (first added on this branch), sitting on top of conventions already established by stamp/: SSH as ubuntu with the shared key ~/.ssh/qb3rt_fleet, one unit reachable at a time over the lab Wi-Fi, and passwordless sudo pre-granted by system/90-qb3rt-sudoers so become: true tasks run unattended.

Inventory

ansible/inventory/hosts.ini hand-lists all 14 units, split into qb3rt_odd and qb3rt_even groups (both rolled up under qb3rt_fleet), mirroring units/<id>.conf. There's no dynamic inventory yet — host/IP pairs are kept in sync by hand.

[qb3rt_odd]
qb3rt-1  ansible_host=192.168.1.101
qb3rt-3  ansible_host=192.168.1.3
...
[qb3rt_even]
qb3rt-2  ansible_host=192.168.2.2
...
[qb3rt_fleet:children]
qb3rt_odd
qb3rt_even

[qb3rt_fleet:vars]
ansible_user=ubuntu
ansible_ssh_private_key_file=~/.ssh/qb3rt_fleet
The machine running ansible-playbook must itself be joined to whichever of ROS_NET_ODD/EVEN it's targeting — same non-bridged-subnet constraint as everything else here. A single playbook run only ever reaches one half of the fleet.

Roles

RolePurpose
https_time_sync Works around the RB3's missing RTC battery. Instead of NTP (whose mid-run clock step can blow up the EKF's covariance), it curls a few HTTPS endpoints, sanity-checks the Date header, and steps the clock once at boot (--bootstrap, wide ±7-day tolerance) then re-checks every 15 min via a systemd timer at a tight ±1h tolerance. Also stops/disables any pre-existing chrony/timesyncd so they don't race the new timer.
ros2_demo_nodes Backfills ros-jazzy-demo-nodes-cpp + ros-jazzy-rmw-cyclonedds-cpp fleet-wide via apt, for units flashed from an image older than the golden image that ships them by default. Idempotent apt install + a package-presence check.

Running a playbook

cd ansible
ansible-playbook playbooks/https-time-sync.yml          # whole current inventory
ansible-playbook playbooks/ros2-demo-nodes.yml -l qb3rt_even   # just EVEN half
ansible-playbook playbooks/ros2-demo-nodes.yml -l qb3rt-6      # just one unit

Use -l <group_or_host> to control blast radius — the standard pattern in this repo is to validate against one unit first, then widen.

5. Accessing units from the laptop

Step 1 — join the right Wi-Fi

Pick ODD or EVEN based on which unit(s) you need; the two subnets are not bridged, so you can only reach one half at a time.

nmcli connection up ROS_NET_ODD      # or ROS_NET_EVEN
ip -4 addr show wlp4s0               # confirm you got a 192.168.<1|2>.x lease
If your laptop is also configured to auto-join other known networks (campus Wi-Fi, eduroam, etc.), NetworkManager can silently roam away from ROS_NET_ODD/EVEN in the background — mid-session connectivity loss to the fleet with no obvious cause is often this, not a robot-side fault. Check nmcli -t -f active,ssid dev wifi | grep '^yes' if something that was working stops working.

Step 2 — SSH to a specific unit

ssh -i ~/.ssh/qb3rt_fleet -o IdentitiesOnly=yes \
    -o StrictHostKeyChecking=accept-new -o UserKnownHostsFile=/dev/null \
    ubuntu@<unit-static-ip>

The robot's ROS 2 environment auto-loads at login via /etc/profile.d/qb3rt-ros-env.sh (domain id, RMW, CycloneDDS URI all set automatically) — nothing extra to source for an interactive shell. For a non-interactive ssh host "command", explicitly source it first, since profile.d isn't guaranteed to run for non-login shells:

ssh -i ~/.ssh/qb3rt_fleet ubuntu@<ip> \
  'source /etc/profile.d/qb3rt-ros-env.sh; ros2 topic list'

Step 3 — talk to a unit's ROS graph from the laptop

# match the unit's domain (== its unit id) and RMW:
export ROS_DOMAIN_ID=<unit id>
export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
export CYCLONEDDS_URI=file://$HOME/cyclonedds.xml   # your fleet peer list, §2

ros2 topic list
ros2 topic hz /imu
ros2 topic echo /imu/data --once
Switching domains often enough to matter? ros2 spins up a separate background daemon per domain the first time you touch it (ros2-daemon --ros-domain-id N ...). These accumulate; if one was started before you last edited cyclonedds.xml it'll be stuck on stale config. pkill -f ros2-daemon clears all of them for a clean slate.

Step 4 (optional) — run the full Nav2 laptop bringup

For the laptop-driven Nav2 workflow (as opposed to ad-hoc topic checks), see laptop/README.md — it covers clock-sync ordering, run order for the robot vs. laptop stacks, and the planner/controller tuning notes. That workflow currently targets a single paired robot (fixed domain in laptop/qb3rt_env.sh), distinct from the fleet-wide monitoring config described in §2 above.
